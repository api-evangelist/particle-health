# Particle Health: ADT Event Subscription

Ground truth: `arazzo/particle-health-adt-subscription-workflow.yml` and
`openapi/particle-health-authentication-api-openapi.yml`,
`openapi/particle-health-patients-api-openapi.yml`,
`openapi/particle-health-subscriptions-api-openapi.yml`,
`openapi/particle-health-hl7v2-api-openapi.yml`.

## Steps

1. **Authenticate** — `GET /auth` (operationId `getAuthToken`) with `client_id` and `client_secret`
   headers. Returns a JWT bearer token valid for 1 hour. Send it as `Authorization: Bearer <token>`
   on every subsequent call.
2. **Register the patient** — `POST /api/v2/patients` (operationId `submitPatient`) with patient
   demographics. Response returns a Particle Patient ID (PPID) — the identifier every later call
   keys off.
3. **Subscribe to ADT/Signal monitoring** — `POST /api/v1/patients/{particle_patient_id}/subscriptions`
   (operationId `createPatientSubscriptions`) to enroll the PPID in Particle Signal for ongoing
   encounter/transition alerts.
4. **Trigger a sandbox event** — in the Sandbox environment only, `POST
   /api/v1/patients/{particle_patient_id}/subscriptions/trigger-sandbox-workflow` (operationId
   `triggerSandboxWorkflow`) synthetically fires a webhook notification so you can test your
   receiver without waiting on a real network event.
5. **Retrieve the resulting HL7v2 message(s)** — `GET /hl7v2/patient/{particle_patient_id}`
   (operationId `getHl7v2Messages`) to pull the raw HL7v2 ADT message(s) generated by the event.

## Rules to carry forward

- Sandbox base URL is `https://sandbox.particlehealth.com` (500 queries/org/day cap); production is
  `https://api.particlehealth.com`. Same request shapes both places.
- Webhook notifications for this flow follow CloudEvents 1.0 with type
  `com.particlehealth.api.v2.hl7v2` and are signed via `X-Ph-Signature-256`
  (`t={unix_timestamp},{hmac_signature}`) — verify the signature before trusting a payload
  (see `asyncapi/particle-health-webhooks.yml`).
- No documented idempotency-key header exists — re-registering the same demographics is expected to
  resolve to the same PPID rather than creating a duplicate (dedup happens server-side on the Master
  Patient Index, per Particle's "Life of a Query" documentation), but this pipeline did not confirm
  that behavior against a live system.
- On `429`, back off ~60s per project (`rate-limits/particle-health-rate-limits.yml`).
